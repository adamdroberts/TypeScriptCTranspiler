## 5. AOT closure requirements

These are not permanent product limits, but every reachable module, native bridge, and runtime-compiled source must be closed over at build time. `tsc2c` should keep rejecting cases it cannot prove or list ahead of time.

- **Runtime code compilation.** Constant `eval(...)` expressions and constant-body `Function(...)` / `new Function(...)` calls compile AOT without `--unsafe-eval`, including earlier local static `const` string aliases, single-valued template-literal type aliases, local const string maps/arrays, numeric literal array indexes, and forms with static parameter-name strings before the final body argument. Function parameter-name strings accept static literals, earlier local static `const` aliases, and single-valued template-literal type aliases. Manifest-listed non-constant eval expressions and function bodies dispatch over the compile-time allow-list, whose entries may be arrays or named object maps; function manifest dispatch uses the final body argument when earlier parameter-name strings, including earlier local static `const` aliases, are static. Unknown source strings still require the gated embedded-Node bridge behind `--unsafe-eval`.
- **Dynamic `require(...)`.** Finite static proofs, including earlier local static `const` string aliases, local variables annotated with inline or type-aliased string-literal union types or finite template-literal string types with string, numeric, bigint, boolean, null, or undefined literal placeholders, local const string maps/arrays with numeric literal array indexes, local const maps with computed static keys, bound `require` forms, and `require.call(module, spec)` / `require.apply(module, args)` / `module.require.call(module, spec)` / `module.require.apply(module, args)` / module-alias `mod.require.call/apply(mod, ...)` / `Reflect.apply(require | module.require | moduleAlias.require | requireAlias, moduleAlias, args)` wrapper forms with inline or earlier static one-element argument tuples, plus `--dynamic-require-manifest` allow lists compile every listed relative or package specifier into the AOT module graph. Manifest `requires` entries may be either an array or a named object map, and unlisted non-finite require sites still reject.
- **Native C++ addons under `node_modules/*/build/Release/*.node`.** Literal native addon specifiers and native-addon packages can now be security allow-listed through a compile-time native-addon manifest, which lowers known `require(...)`/import bindings to `runtime/tsc_node_embed.cc` via `tsc_node_native_addon(<manifest path>)` and links `libnode` without enabling the unsafe eval/Function bridge entry points. Package `exports` / `imports` condition maps, package-private `#...` imports, and package-private imports that target external native-addon packages are included in the native-addon closure checks, direct `.node` default imports are typed as `any` for manifest-backed bridge imports, and `bun run test:native-addon-smoke` validates a real N-API addon path when `libnode` is available. Manifest-backed package-private imports to external native-addon packages lower through the embedded Node bridge, and manifest-backed `require(...)` destructuring reads named properties, applies default initializers for `undefined` bridge properties, or materializes rest objects from the bridge value. Unlisted native addons still reject.
