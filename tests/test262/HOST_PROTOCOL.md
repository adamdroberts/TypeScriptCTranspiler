# Test262 host protocol

`run.ts` owns pin verification, Test262 discovery, YAML parsing, edition classification, strict/sloppy/module/raw scenario expansion, harness ordering, sharding, timeouts, result-set identity, and exact negative-result judging. A host owns only faithful execution in generated C and the tsc2c runtime.

The host executable must support two calls:

- `HOST ... --describe` prints one JSON `HostDescription` matching the reviewed `compliance/ecmascript-2026/host-profile.json` exactly.
- `HOST ... --request FILE` reads one JSON `HostRequest` from the named runner-owned temporary file and prints one JSON `HostPreparation` to stdout.

Protocol version 4 binds both calls to the reviewed execution contract and the SHA-256 of the complete sanitized effective environment. A claim-eligible profile must use `tsc2c-runner-owned-native-v1`; the diagnostic contract can never become claim evidence merely by changing capability flags. The runner resolves and hashes the exact host executable, hashes the complete reviewed compiler/runtime/runner implementation worklist and dependency lock inputs, and rejects any bytes written to stderr outside the single-JSON protocol.

For a claim-eligible profile, the host must evaluate each `setupScripts` entry as a separate global Script, in order, in one fresh Realm; then evaluate `testSource` as the root named by `testPath` with the requested Script or Module goal. It must not concatenate or wrap these sources. `raw` requests have no setup scripts and the test source is byte-for-byte unchanged, while host-defined `print` and `$262` bindings still exist out of band.

For every scenario, `moduleFiles` is the complete pinned sibling-resource directory derived from the independently verified Test262 Git tree. Supplying it unconditionally avoids guessing from flags or source syntax whether computed, eval-created, or otherwise dynamic module loading can occur. It includes JavaScript and non-JavaScript resources and may include files whose names do not contain `_FIXTURE`; those files are dependencies, never extra standalone scenarios in this request. Resolve every Test262 `./name` specifier against `moduleBasePath` and only to the exact supplied path. The root `testPath` is supplied separately as `testSource` and remains the canonical module-graph entry if a cycle resolves back to it. A missing supplied path is a resolution failure, and the host must not read alternate module sources from the ambient filesystem. If a future pin introduces query/fragment module identities, the runner protocol must be revised and self-tested before that pin is accepted; the current pinned corpus has no such relative specifier.

The host prepares artifacts; it does not report a conformance verdict or author the native execution transcript. `artifactDirectory` is an ephemeral runner-owned output root and is excluded from the stable request identity. On successful compilation, the host returns the normalized generated-C path, native-executable path, and complete sorted artifact worklist. On an exact parse/resolution compiler failure, it returns the structured observation plus a diagnostics artifact. A diagnostic-only host may return a wrapped non-claimable observation. Every host and local-gate command runs below the runner-built Linux child-subreaper supervisor. The supervisor drains one process worklist across process-group and `setsid()` boundaries; a timeout, containment error, or descendant left after the primary command exits fails the evidence run.

The runner independently walks the declared artifact worklist, rejects missing/extra files, directories outside the worklist, symlinks, hard links, path escapes, oversized files, and non-native/delegated engine artifacts, then hashes and seals every accepted file. For runtime scenarios the executable must be a dynamically loaded Linux x86-64 ELF. The supervisor injects the runner-built guard before `main`; a pipe handshake proves that `no_new_privs` and the seccomp filter were installed. That filter forbids further process execution, process creation, executable-memory creation, and process/mount/namespace mutation, so the sealed program cannot hand semantics to another engine or leave an executable descendant. The runner accepts exactly one JSON observation and rehashes the complete artifact set after execution. The compiled program may report only normal completion or a runtime throw; it cannot supply its own transcript. For compiler-negative scenarios, the runner hashes the exact diagnostics artifact and attaches the compiler observation. The runner-authored transcript binds the stable request, reviewed implementation, complete artifact manifest, generated-C/native or diagnostic paths, process-supervisor and native-guard binaries, and observed process exit. The claim checker deterministically rebuilds those containment binaries from their tracked C sources and compares their identities. Missing, extra, changed, host-authored, delegated, unguarded, or structurally inconsistent evidence fails closed.

An observation describes behavior, never pass/fail. A throw identifies the exact `parse`, `resolution`, or `runtime` phase, the thrown value's constructor name, and its origin: `test-source`, `module-graph`, `setup-script`, or `async-completion`. Only a root-test or dependency-graph throw can satisfy negative metadata. A harness/setup failure and `$DONE(error)` are test failures even when their constructor happens to match expected negative metadata. Unsupported compiler diagnostics never satisfy negative tests. Async `normal` is valid only after the `$DONE` protocol reports completion. The host must configure the current Agent Record's `[[CanBlock]]` value from `canBlock` when it is non-null. A timeout, crash, missing host hook, or unclassifiable result is explicit and claim-blocking.

The current `native-host.ts` prepares real generated-C/native artifacts and structured compiler failures under the runner-owned contract, but its reviewed profile remains claim-ineligible while any required capability is disabled. `diagnostic-host.ts` remains only as a protocol-negative test fixture and cannot produce claim evidence. Changing `claimEligible` to true requires implementing and independently testing every capability in the baseline. Executing the tested semantics in embedded Node, another JavaScript engine, or an unsafe-eval fallback is semantic delegation and is forbidden as conformance evidence. Artifact attestations bind results to the exact reviewed source revision and trusted GitHub-hosted release workflow; they do not make an unreviewed or deliberately dishonest runner revision trustworthy.
